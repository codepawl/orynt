# CodePawl Execution Plan

## Execution principles

CodePawl turns every AI coding session into measurable engineering work. The execution roadmap must protect that thesis while moving from an empty/local repo toward a useful CLI, local history, Studio, and GitHub Action.

Principles:

* Local-first by default. Local CodePawl must work without CloudPawl, auth, billing, desktop packaging, GitHub App, or a cloud account.
* Session Intelligence and report quality come before dashboard polish. The first durable value is understanding what happened, what evidence exists, and what to do next.
* Fixture and real-repo dogfooding both matter. Every milestone should keep a deterministic fixture path and a real current-repo path working.
* Deterministic checks come before AI diagnosis. Diff/status parsing, validation evidence, risk rules, and report structure must be useful without AI.
* No cloud required for MVP. Do not add Clerk, Stripe, CloudPawl sync, GitHub App backend, enterprise/self-host, or source-upload implementation during local MVP work.
* Rust owns local core, CLI, daemon, SQLite store, evidence parsing, and report generation.
* TypeScript owns Studio UI, GitHub Action wrapper, GitHub App/backend later, and CloudPawl web surfaces later.
* Keep each sprint small enough to validate with concrete commands before moving to the next surface.

## Milestone overview

### v0.1 CLI and local history

Goal: produce useful local reports from fixture sessions and real git repos, then persist report history.

Done when:

* `codepawl analyze --fixture fixtures/sessions/basic` works.
* `codepawl analyze` works on a real git repo.
* Reports include verdict, risks, evidence references, and next actions.
* Reports export JSON and Markdown.
* SQLite stores project, session, and report history.
* `codepawl report --last` works.

### v0.2 Local Studio

Goal: show local project, session, and report data in Studio without becoming a vanity dashboard.

Done when:

* Local Studio can view project/session/report data.
* Session detail is the first-value surface.
* The UI can render report JSON generated by the Rust core.
* Empty states guide users to analyze a fixture or current repo.

### v0.3 GitHub Action

Goal: bring CodePawl reports into pull requests without requiring CloudPawl.

Done when:

* GitHub Action can run CodePawl in CI.
* It generates a PR-ready report.
* It writes a job summary and uploads report artifacts.
* It can fail the check according to a configured verdict threshold.
* It works without a CloudPawl account or token.

### v0.4 Agent hooks

Goal: start ingesting real agent session events without forcing users into a wrapper workflow.

Done when:

* At least one opt-in hook integration writes local JSONL events.
* Hook events are normalized into sessions.
* Analysis can use captured events plus git evidence.
* Users can disable the integration cleanly.

### v0.5 Desktop and cloud preparation

Goal: prepare packaging, distribution, and cloud-ready boundaries without implementing CloudPawl.

Done when:

* CLI release/distribution skeleton exists.
* Local data and artifact boundaries are documented and stable enough for later Studio/desktop/cloud work.
* CloudPawl remains optional and unimplemented.

## Sprint breakdown

## Sprint 0: Foundation and fixture report

### Goal

Create the minimal project foundation and prove one fixture session can produce a stable local report.

### Context to inspect

* `.codex/plan/master_plan.md`
* `.codex/plan/technical_plan.md`
* `.codex/plan/design_plan.md`
* `.codex/plan/business_plan.md`
* Current repository structure
* Existing assets and planning-only files

### Scope

* Establish the minimal Rust-first workspace shape only when implementation begins.
* Add `mise` tool pinning for Rust, Node, pnpm, and future shared tools.
* Add `just` recipes for common validation commands.
* Create the first fixture path: `fixtures/sessions/basic`.
* Implement enough analysis and rendering for `codepawl analyze --fixture fixtures/sessions/basic`.
* Produce `report.json` and `report.md` with verdict, evidence references, risks, and next action.
* Add initial fixture and snapshot tests for the basic report output.

### Do not build

* Do not build Studio.
* Do not add SQLite yet unless needed for basic command plumbing.
* Do not add GitHub Action, hooks, desktop, auth, billing, CloudPawl, or GitHub App.
* Do not build full release automation.

### Done when

* `codepawl analyze --fixture fixtures/sessions/basic` produces a JSON report and Markdown report.
* The report includes a verdict, evidence references, risks, and next action.
* Fixture output is covered by tests or snapshots.
* `just check` runs the expected local checks.

### Validation commands

```bash
mise install
just check
cargo test --workspace
codepawl analyze --fixture fixtures/sessions/basic
```

## Sprint 1: Real git repo analysis

### Goal

Make CodePawl analyze the current git repository without fixture mode.

### Context to inspect

* Git diff/status/branch behavior in the local repo
* Technical plan sections for local core, git inspection, evidence parser, and report engine
* Initial Sprint 0 report contract and snapshots

### Scope

* Implement `codepawl analyze` for a real git repo.
* Read git branch, status, changed files, and diff summary.
* Detect basic file risk categories such as lockfiles, config files, migrations, generated files, and unrelated-looking changes.
* Detect available validation evidence from known logs or command records when present.
* Keep JSON and Markdown report shape compatible with Sprint 0.

### Do not build

* Do not add Studio or dashboard views.
* Do not add SQLite history beyond what is unavoidable for command output.
* Do not add AI diagnosis.
* Do not add GitHub Action or hooks.

### Done when

* `codepawl analyze` works inside a real git repo.
* The report identifies branch, changed files, evidence references, risks, and next action.
* Fixture mode still works.
* Tests cover fixture and real-repo-style analysis through controlled test repos or fixtures.

### Validation commands

```bash
just check
cargo test --workspace
codepawl analyze --fixture fixtures/sessions/basic
codepawl analyze
```

## Sprint 2: Report quality gates

### Goal

Make reports reliable enough to be the product's first value surface.

### Context to inspect

* Report format requirements from master and technical plans
* Design plan sections for Session Detail, evidence, risks, next actions, and GitHub report design
* Existing fixture snapshots

### Scope

* Enforce that every report has a verdict.
* Enforce that every risk cites at least one evidence reference.
* Enforce that every report includes a next action.
* Stabilize JSON and Markdown rendering.
* Add fixtures for safe, risky, blocked, and missing-evidence cases.
* Add snapshot tests for report output.
* Add deterministic policy/rule checks before any AI-assisted diagnosis.

### Do not build

* Do not polish dashboards before report quality is stable.
* Do not add cloud upload or AI artifact upload.
* Do not add GitHub comment rendering until local report quality is stable.

### Done when

* Missing verdict, uncited risks, or missing next action fail tests.
* JSON and Markdown reports remain stable under snapshots.
* Fixture cases cover safe, risky, blocked, and missing-evidence outcomes.
* Real-repo analysis still produces a usable report.

### Validation commands

```bash
just check
cargo test --workspace
codepawl analyze --fixture fixtures/sessions/basic
codepawl analyze --fixture fixtures/sessions/missing-evidence
codepawl analyze
```

## Sprint 3: SQLite store and session history

### Goal

Persist local project, session, and report history while keeping raw artifacts on the filesystem.

### Context to inspect

* Technical plan Platform 2: Local Store Platform
* Local layout under `~/.codepawl/`
* Report JSON contract from Sprints 0-2

### Scope

* Add SQLite storage for local projects, sessions, reports, evidence metadata, risk items, and artifact indexes.
* Store raw large artifacts on the filesystem, not directly in SQLite by default.
* Add migrations and migration tests.
* Persist reports generated by fixture and real-repo analysis.
* Implement `codepawl report --last`.
* Keep SQLite as the local source of truth only.

### Do not build

* Do not add CloudPawl sync or remote database assumptions.
* Do not add Studio until CLI/local history is usable.
* Do not store raw source, huge logs, or raw artifacts directly in SQLite by default.

### Done when

* Reports persist across process runs.
* `codepawl report --last` returns the latest report.
* Project/session/report history can be queried locally.
* SQLite migrations are tested.
* Fixture and real-repo analysis both persist history.

### Validation commands

```bash
just check
cargo test --workspace
codepawl analyze --fixture fixtures/sessions/basic
codepawl report --last
codepawl analyze
codepawl report --last
```

## Sprint 5: GitHub Action

### Goal

Generate PR-ready CodePawl reports in CI without requiring CloudPawl.

### Context to inspect

* Technical plan Platform 5: GitHub Platform
* Business plan GitHub strategy
* Design plan GitHub report design
* Local report format and quality gates from v0.1

### Scope

* Add a TypeScript GitHub Action wrapper after local CLI reports are stable.
* Run the Rust `codepawl` binary in CI.
* Generate PR-ready Markdown from the local report.
* Write `$GITHUB_STEP_SUMMARY`.
* Upload `report.json` and `report.md` artifacts.
* Support fail-on behavior mapped to the CodePawl verdict taxonomy.
* Keep optional CloudPawl token handling out of the first implementation unless only documented as future behavior.

### Do not build

* Do not require a CloudPawl account or token.
* Do not build GitHub App.
* Do not upload source, diffs, logs, or raw artifacts to CloudPawl.
* Do not add sticky PR comments, PR commands, or line-by-line PR comments in the Action v0 scope.

### Done when

* GitHub Action can generate a PR-ready report.
* It writes a job summary.
* It uploads report artifacts.
* It can fail according to the configured verdict threshold.
* It works with no CloudPawl account or token.

### Validation commands


## Sprint 6: Agent hook ingestion

### Goal

Capture AI coding sessions through opt-in hooks without changing the user's primary agent workflow.

### Context to inspect

* Technical plan Platform 4: Agent Integration Platform
* Master plan UX principle: avoid wrapper-first workflows
* Local inbox and artifact layout
* SQLite session/event schema from Sprint 3

### Scope

* Add one opt-in hook ingestion path first.
* Write local JSONL events into `~/.codepawl/inbox/`.
* Normalize hook events into session events.
* Link captured events with git diff/status evidence.
* Allow users to disable the integration cleanly.
* Preserve allowlisted project paths and secret redaction defaults.

### Do not build

* Do not make `codepawl run claude` or `codepawl run codex` the primary UX.
* Do not capture unallowlisted projects.
* Do not capture `.env`, SSH keys, or ignored secret paths by default.
* Do not upload hook data to cloud.

### Done when

* One hook integration writes local JSONL events.
* Ingest creates a session from those events.
* Analysis can use captured events plus git evidence.
* Users can disable the integration.
* Fixture and manual analysis paths still work.

### Validation commands

```bash

codepawl analyze --fixture fixtures/sessions/basic
codepawl analyze
```

* Rust toolchain
* Node
* pnpm
* `just`
* future helper tools as needed

Use `just` for project recipes:

* `just check`
* `just test`
* `just fmt-check`
* `just fixture`
* `just analyze-current`
* `just studio` later
* `just action-test` later

Testing sequence:

* Start with `cargo test --workspace`.
* Add `cargo-nextest` later only when the Rust test suite grows enough to justify it.
* Add TypeScript test/build commands when Studio or GitHub Action work begins.
* Add `cargo-dist` later for distribution; do not build full release automation in v0.1.

## Quality gates

Every report must satisfy these gates:

* Every report has a verdict.
* Every risk cites evidence.
* Every report includes a next action.
* Every major claim is evidence-bound to a file, command, log, diff, policy rule, or session event.
* JSON and Markdown report outputs remain stable.
* Fixture tests and snapshot tests cover report output.
* Fixture-based analysis and real current-repo analysis both keep working.
* Reports remain useful without AI diagnosis.
